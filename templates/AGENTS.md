# AGENTS.md — Craftsman Engineering Standard

This repository uses **Craftsman**: every change is reviewed and verified against an evidence ledger before it counts as done.

## The Craftsman loop
- **Build freely, review hard:** no gate activity while building. The gate judges the final diff: fresh-context hunters covered every hunk, every finding has a verdict with evidence, the tests pass on the final code. Users write plain words; infer target, fixing and depth yourself.
- **Depth:** one adaptive depth. `craftsman review prepare` goes deep by itself on a security or concurrency signal in a production hunk or a large change (over 250 changed production lines); add your own judgment with `--deep` by the rules in `/craft-review` (Depth), or start with `/craftsman --deep` / `ultracraft`. Deep adds every lens on every production hunk, a fresh second look and an end-to-end run.
- **Start (`/craftsman` only):** `craftsman gate --init [--deep] --task "<request>"` records the base commit; the review always covers the whole diff since then (standalone `/craft-review` without fixing does not start a gate session).
- **Review:** write the intent brief (3-8 claims about what the change must do), then `craftsman review prepare --task-file -` freezes the diff, decides the depth and prints the hunt plan: one slot per hunter (its hunks and lenses), computed from the diff. Launch every slot together as a fresh-context `craftsman-reviewer` subagent whose whole prompt is the line `prepare` prints: `You are Craftsman hunter <ID>. Run craftsman review brief <ID> and follow it exactly.` The brief gives the slice, the lenses and the commands that record the work: `craftsman review add --hunter <ID> ...` for every candidate, `craftsman review cover --hunter <ID> --hunks <ids> --note "..."` for what was examined. Then end the turn, run `craftsman review check` and do what it lists.
- **Verify and saturate:** `check` names the clusters of findings without a verdict; launch one `craftsman-verifier` subagent per cluster with the prompt `You are a Craftsman verifier. Run craftsman review brief --verifier <IDS> and follow it exactly.` Verifiers merge duplicates (`craftsman review merge <target> <dup>`, only when one fix removes every consequence), try to disprove each finding, and record `craftsman review verdict`; a dismissed `blocker` or `major` without a run needs a second verifier. A `proven` (or serious `probable`) defect makes `check` store a further wave of slots (variant hunters `W2-F<n>`, a fresh set `W2-X<j>`, at most 3 generations); launch them like the first.
- **Fix:** fix confirmed defects at the root cause with a regression test and confirm each fix (the test, or the verifier that judged it); `craftsman review resolve <id> --as fixed --note "..."`; then `craftsman review prepare` again: the fix delta becomes a small round whose slots fresh hunters work through.
- **Run checks through the ledger:** `craftsman run --kind test -- <command>` (and `--kind e2e` when deep); only runs on the final code count.
- **Enforcement:** where hooks serve the session (Claude Code, Copilot, Antigravity) finishing needs every slot done; where none do (Codex, Cursor) the round is advisory, complete when every hunk is covered, and the report says `SELF-REVIEWED`.
- **Done means** `craftsman review check` passes; then `craftsman gate --complete` and report with `craftsman review report` (in standalone review-only `/craft-review`, finish with `craftsman review check --review-only` and `craftsman review report --review-only`).
- **Skills & lenses:** invoke `/name` as a skill if your platform offers it; otherwise run `craftsman skill show <name>` (and `craftsman skill show craft-review --lenses <lenses>` for the playbooks of the lenses you apply). Never search the file system for skill or lens files.

## Search scope
- Work only inside this git work tree (`git rev-parse --show-toplevel`): prefer `git ls-files`, `git grep`, and editor search scoped to this folder.
- Outside the work tree you may read only an exact file cited by a stack trace/error, a temp directory you created, CI logs for this branch/PR, or Craftsman's own data via `craftsman …` CLI commands (never open `.git/craftsman` files by hand except a packet, view, scratch or inbox path that `craftsman review prepare`, `show`, `view`, `scratch` or `inbox` prints for this repository).
- Batch JSON files go only to `craftsman review inbox` paths; never to `%TEMP%` or into the repository; a file you had to create elsewhere must be deleted before you report.
- Never run recursive searches of `~`, `/`, or parent directories, and never open other repositories, other projects' packets/ledgers/reports, or assistant session stores.
